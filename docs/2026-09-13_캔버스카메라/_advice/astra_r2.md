# 캔버스 카메라 도입 자문 — 2라운드

**권고를 ‘부분 채택’에서 ‘보정 후 제한적 재판정, 현재 결과물의 본편 투입은 보류’로 좁힌다.** 흐름은 카메라를 더 시험할 가치가 있고, 개념의 상태 교체는 독립 후보로 남긴다. 현재 비교 B의 단일 카드 팬과 목록 B의 마지막 축소는 채택 근거가 약하다. 네 장면의 결과를 합쳐 카메라의 우위를 선언할 수 없다.

판정 전에 반드시 바로잡을 것은 세 가지다. **A가 좋은 현행 구현을 대표하는지**, **마지막 축소에서 결론을 처음 읽게 만드는지**, **‘검증 완료’라는 설명이 원본 로그와 맞는지**다. 특히 `B_seek_determinism.txt` 끝의 `MISMATCH(>50px): 17`은 요약에 누락되어 있다.

검토 범위: 브리프의 지정 문서·게이트 요약·헬퍼·타임라인·판정 HTML을 읽고 JPG 시트 8장을 모두 직접 확인했다. 추가로 1라운드 답변, A/B 생성 스크립트, 공용 마크업·CSS, A 개념 마크업·CSS, 생성된 A/B HTML의 관련 부분, `check_motion.py`, seek·재캡처·자막 밴드 원본 로그를 확인했다. 생성 HTML의 흐름·목록·비교 `section`은 문자열 비교로 A/B 동일함을 확인했다. 헬퍼의 등록 로직은 간단한 Node 모의 객체로 확인했다.

**영상·음성을 정상 속도로 재생하거나 캡처를 다시 실행하지는 않았다.** 따라서 발화와 실제 가독 시점의 오차, 이동 피로, 정확한 읽기 성공 여부는 시트로 판단 불가다. 아래에서 코드로 확인한 사실과 시트 관찰을 구분하며, 효과나 원인에 관한 미검증 해석은 ‘추측’으로 표시한다.

## 1. 실험 공정성: 통제 실험으로는 유용하지만 ‘현행 대비 개선’의 증거로는 부족하다

### 1-1. 같은 것과 다른 것

| 항목 | 확인 결과 | 판정에 미치는 영향 |
|---|---|---|
| 흐름·목록·비교의 텍스트·카드·배치 | 생성 HTML의 해당 세 `section`은 A/B 동일하다. `buildA.py`는 B의 마크업과 타임라인을 재사용하고 `__CAM_FIXED`를 켠다. | A에서 정보 자체를 뺀 실험은 아니다. 같은 캔버스에 카메라를 적용하는 효과를 보는 데는 적절하다. |
| 세 유형의 리빌 큐 | 같은 `timelines.js`를 사용한다. A에서도 `ghost`, `fade`, `draw`가 작동하며 카메라 이동만 무시된다. | A는 ‘움직임이 없는 카드 슬라이드’가 아니다. 다만 A의 등장 문법도 B의 실험 헬퍼를 쓰므로 ‘기존 preset 그대로’라는 이름은 부정확하다. |
| 화면상 크기 | 같지 않다. 보고된 A 고정 배율은 흐름 0.86, 목록 0.70, 비교 0.67. B는 부분 샷에서 커지고, 최종 fit은 각각 0.81, 0.66, 0.63이다. | 같은 CSS 글자 크기는 같은 시청 크기가 아니다. 확대·축소의 이익과 비용은 카메라 처치 자체에 포함되지만, A의 기본 가독성까지 부족하면 현행 대비 우위를 말하기 어렵다. |
| A/B 전체 보기 여백 | A의 고정 분기는 `pad:60`을 강제한다. B 최종 fit은 흐름 110, 목록·비교 100이다. | B의 최종 글자는 A보다 약 6% 작다. 카메라 유무 외에 최종 프레이밍 정책도 달라진다. |
| 개념의 정보·등장 | 같은 팀장·신입·업무 전달·보고 부재·상태 변화 내용을 사용하지만, A는 카드와 인물 묶음을 늦게 등장시키고 B는 틀을 먼저 보여준다. 상태 전환도 CSS stage와 GSAP swap으로 다르다. | 의도된 ‘등장·상태 교체 묶음’ 실험이다. 모든 장면에 ‘같은 등장 시각’이라고 쓰면 안 된다. |
| 음성·자막·출력 | 문서는 동일 음성과 타임베이스를 사용했다고 보고한다. 판정 페이지는 `_audio.mp4`를 참조한다. | 파일의 음성 동일성·음량·최종 자막 합성·인코딩 동등성은 이번 검토에서 독립 검증하지 않았다. 시트로 판단 불가다. |

**‘화면상 글자 크기가 다르다’는 사실 자체가 실험 실패는 아니다.** 1라운드도 화면상 크기 변화는 카메라의 이익·비용으로 평가하도록 했다. 문제는 A가 B용 큰 캔버스를 한 번에 축소한 구현이라는 점이다. 이 실험은 ‘같은 큰 캔버스에서 고정과 이동 중 무엇이 나은가’에 답할 수 있지만, ‘우리가 만들 수 있는 좋은 고정 화면보다 나은가’에는 아직 답하지 못한다.

### 1-2. A가 불리한 지점

1. **미래 요소의 자리까지 처음부터 확보한다.** 흐름 A는 오른쪽 분기와 마지막 `.n5`까지, 목록 A는 세 행과 결론 칩까지, 비교 A는 위 기준 카드와 아래 양쪽 카드까지 포함한 고정 구도다. 초반에는 작은 카드만 화면 구석이나 위쪽에 남는다. 추측: 이 빈 공간과 작은 글자가 B의 중심 배치·부분 확대를 실제 효익 이상으로 돋보이게 할 수 있다.
2. **‘좋은 현행 레이아웃’으로 최적화한 A가 아니다.** 비교는 기준과 두 조건을 더 밀집해서 배치할 수 있고, 목록은 카드 높이·행간·결론 공간을 조정할 수 있다. 단, 개선 A를 만들면 그것은 순수 카메라 유무 실험과 별개의 실무 비교가 된다. 지금 A를 버리지 말고 `A0=동일 캔버스 고정`, `A1=현행 방식의 좋은 고정 구현`으로 구분하는 편이 정확하다.
3. **개념 A는 도입의 시각적 반응이 늦다.** A의 팀장 카드 등장 지연은 1.10초, 신입은 2.46초다. B는 0초와 0.25초부터 틀을 예고한다. 이는 처치의 일부지만, B가 좋다는 평가가 ‘틀 예고’ 때문인지 ‘A 초반이 비어 있기 때문’인지는 분리되지 않는다.
4. **A 개념도 이미 같은 신입 카드 안에서 상태를 교체한다.** `s1A.html`의 두 `.stage`는 같은 카드의 `stages-container` 안에 있다. 따라서 ‘A는 정체성이 끊기고 B만 제자리 교체를 한다’는 해석은 성립하지 않는다. 실제 차이는 전환 방식·시간·틀 예고의 조합이다.

### 1-3. B가 불리한 지점

1. **마지막 구도가 더 작다.** 동일 대상에 더 큰 padding을 주므로 B 최종 샷은 A보다 불필요하게 불리하다. 최종 fit의 효익을 평가하려면 대상 집합과 여백을 맞추거나, 다른 여백을 별도의 연출 선택으로 명시해야 한다.
2. **카메라 상한이 작은 초기 카드를 구제하지 못한다.** 흐름 첫 카드 `.n0`는 폭 540px로 디자인 화면 폭의 약 28%다. 배율이 이미 1이면 pad를 줄여도 커지지 않는다. `03_리스크.md`의 ‘카드 기본 크기 상향 또는 pad 축소’ 중 후자는 이 상황의 해법이 아니다. 카드와 타이포를 함께 다시 설계해야 한다.
3. **비교의 카메라 단위가 1라운드 권고와 다르다.** 권고는 비교 축과 양쪽 셀을 함께 잡는 행 중심 프레이밍이었다. 실제 B는 `.k → .L → .R`을 따로 잡는다. 현재 B가 지더라도 ‘비교형 카메라 전체가 무효’라고 일반화해서는 안 된다.
4. **가독성 검사를 통과하기 전 이동·fit을 넣었다.** 특히 비교는 마지막 중요한 부정 라벨을 보여준 직후 이동하고, 전체 구도를 충분히 유지하지 못한다. 이는 카메라 방식의 필연적 한계와 현재 큐 설계의 결함을 섞는다.

## 2. 시트에서 보이는 결함과 타임라인 대조

시간 표기 규칙: **클립 시작 기준의 대략적인 초**다. 브리프대로 왼쪽 위부터 6열을 세어 첫 칸을 0초로 부른다. 시트에는 타임스탬프가 없어 추출 프레임의 정확한 PTS·첫 샘플 오프셋을 확인할 수 없다. 따라서 ‘9초 칸’은 프레임 단위 실측 시각이 아니며, 아래 소수점 시각은 별도로 코드에서 계산했다. 빨간 빈 칸과 구분선은 시트의 채움 영역으로 취급했으며 영상의 빨간 화면으로 세지 않았다.

## 3. 코드 비평: 제한된 실험 구현이지 계약이 완성된 공용 헬퍼는 아니다

### 3-1. 충족한 부분

- 카메라가 별도 `.canvas`의 `x/y/scale`을 소유하고, 요소 리빌과 슬라이드 전환을 다른 계층에서 처리한다.
- `shot/fit`은 타임라인을 만드는 단계에서 좌표를 계산한다. 재생 중 매 프레임 DOM을 측정하거나 벽시계·난수로 누적 이동시키지 않는다.
- 카메라 트윈은 명시적인 양끝 값과 GSAP `fromTo`를 사용한다. 현재 네 타임라인의 카메라 호출은 시간순이며 카메라끼리 겹치지 않는다.
- 제공된 `fit` 호출은 대상 선택자를 명시하며, opacity를 검사해 대상을 바꾸지 않는다.
- 정상적인 양수 옵션과 정상 bounds에서는 `Math.min(..., 1)`로 카메라 배율 상한 1을 지킨다.
- 생성 HTML의 구동부는 기존 `totalTime(v+0.001,true)`와 `totalTime(v,false)` 두 호출을 유지한다.

이것들은 좋은 출발점이다. 그러나 ‘fromTo 사용’, ‘직전 상태 사용’, ‘반복 캡처 일치’ 중 하나만으로 임의 seek·재빌드까지 안전해지는 것은 아니다.

### 3-2. 결정론의 증거가 과장되어 있다

**원본 seek 로그부터 정리해야 한다.** `B_seek_determinism.txt`에는 다음이 함께 있다.

- 일부 행의 마지막 필드에 `(0.0, 0)`이 있다.
- 128.28초 행의 앞 두 결과는 `(2.3575, 43737)`과 `(0.0, 0)`으로 다르다.
- 비교 구간 298.6~313.83초의 여러 행은 앞 두 결과가 모두 `(0.0, 0)`이다.
- 마지막 집계는 `MISMATCH(>50px): 17`이다.

로그에는 열 이름과 실행 조건이 없다. 따라서 ‘17개가 모두 새 페이지 직행 대 순방향의 실패’라고 단정할 수도 없지만, **이 파일을 근거로 무조건 ‘7지점 픽셀 차이 0, 결정론 안전’이라고 요약할 수도 없다.** 추측: 서로 다른 seek 경로의 성공·실패를 한 로그에 섞었거나, 이전 실패 결과가 남았을 수 있다. 어느 경우든 빌드 식별자·비교 경로·실제 활성 슬라이드·차분 지표를 명시한 새 로그가 필요하다. 백색 화면끼리의 일치도 성공으로 세지 않도록 기대 콘텐츠의 존재를 확인해야 한다.

`B_recapture_diff.txt`가 직접 뒷받침하는 것은 **T1 흐름 한 구간의 반복 캡처 560프레임 일치**다. 네 장면 전체, A, 역방향, 임의 순서, 청크 경계의 일치를 뜻하지 않는다.

생성 HTML의 `seekApplied`가 앞으로만 증가하는 것도 확인했다. 장면을 넘었다가 과거로 돌아갈 때 이벤트·슬라이드 상태를 재구성하지 않으므로, 1라운드의 역방향/임의 순서 seek 계약은 시스템 전체에서 미충족이다. ‘기존 템플릿도 그랬다’는 회귀 여부 설명이지 계약 충족의 증거가 아니다. 당분간 새 페이지·순방향 캡처만 지원한다면 그 범위를 명시하고, 헬퍼 주석의 ‘seek 왕복 안전’은 제거해야 한다.

### 3-3. `immediateRender` 규칙의 남은 구멍

**첫째, 실제 구현은 ‘요소별 첫 트윈’이 아니라 ‘선택 집합에 새 요소가 하나라도 있으면 전체 즉시 렌더’다.**

```js
const first = els.some(e => !seen.has(e));
to = Object.assign({}, to, { immediateRender: first });
```

이미 등록한 요소와 새 요소가 같은 선택자에 잡히면, 기존 요소에도 `immediateRender:true`가 적용된다. Node 모의 등록으로 `fade(one) → fade(both)`를 호출했을 때 두 번째 호출도 `true`임을 확인했다. 이는 브라우저의 실제 화면 재현 시험은 아니지만, 규칙과 구현이 다르다는 점은 확정이다. 현재 네 장면에서 이 혼합 선택으로 깨졌다는 증거는 없다. 공용화 전에 요소별로 나누거나 등록 단계에서 초기 상태를 별도로 확정해야 한다.

**둘째, `reset(canvasSel)`은 `state`만 지우고 `seen`은 지우지 않는다.** 같은 DOM에 새 타임라인을 만들면 ‘첫’ 트윈이 더 이상 즉시 렌더되지 않는다. 모의 등록에서도 reset 후 같은 요소가 `immediateRender:false`로 남았다. 반대로 기존 타임라인도 제거하지 않으므로 reset만으로 안전한 재빌드가 되지 않는다. 상태·초기화 기록·타임라인 수명을 함께 관리해야 한다.

**셋째, 요소 단위 기록은 속성별 초기화를 보장하지 않는다.** `draw()`는 같은 path에 opacity 트윈을 먼저 등록하고 dashoffset 트윈을 뒤에 등록한다. 후자는 첫 호출이어도 즉시 렌더가 꺼진다. 현재는 opacity 0이 선을 가려줄 수 있지만, 이후 다른 구성에서도 모든 속성의 t=0 상태가 준비된다는 보장은 없다. 직접 작성한 `tl.fromTo`도 `seen`을 거치지 않는다. ‘헬퍼를 썼으므로 자동으로 안전’이라는 규칙 대신 명시적인 초기 상태와 후속 트윈 정책을 가져야 한다.

### 3-5. fit 대상과 배율

**명시성은 부분 충족이다.** 실제 호출에서 선택자는 적었지만 `.cv-item`은 의미별 대상 ID 목록이 아니다. 마크업에 새 `.cv-item`을 추가하면 과거 Scene의 fit 대상이 조용히 달라진다. 현재 모든 항목을 마지막에 포함하는 것은 의도일 수 있으나, 공용 API의 암묵 기본값 `o.targets || '.cv-item'`은 1라운드의 엄격한 Scene별 집합 계약보다 느슨하다. fit의 `targets`를 필수로 하고 빌드 시 최종 대상 목록을 기록하는 편이 낫다.

미래 요소를 준비 단계에서 측정하는 것 자체는 문제없다. 문제는 미래 요소 때문에 불필요하게 축소되거나, 아직 말하지 않은 의미를 보여주는 것이다. 흐름 `.n5`를 fit에 넣는 것과 그 내용을 언제 읽히게 할지는 별도로 감사해야 한다.

**scale≤1은 정상 입력에서 충족하지만, 가독성 계약은 충족하지 않는다.** 음수 zoom, 지나친 pad, 0 크기, NaN 등에 대한 방어가 없다. 양수·유한수·유효 안전영역 검증을 추가해야 한다. 허용 이징도 제한하지 않아, 최종 값이 1이어도 overshoot 이징까지 포함한 모든 중간 프레임의 상한을 보증하지는 않는다. 현재 기본 `power2.inOut`에서 그런 overshoot가 관찰됐다는 뜻은 아니다.

보고된 fit 배율로 계산하면 다음과 같다. 원본 크기는 현재 CSS의 예이며 실제 요소별 override는 따로 확인해야 한다.

| 원본 토큰 | 흐름 B 0.81 | 목록 B 0.66 | 비교 B 0.63 |
|---|---:|---:|---:|
| 26px 칩 | 약 21.1px | 약 17.2px | 약 16.4px |
| 22px 보조 라벨 | 약 17.8px | 약 14.5px | 약 13.9px |
| 3px 관계선 | 약 2.43px | 약 1.98px | 약 1.89px |

상한 1은 확대 과잉을 제한할 뿐, 축소 후 최소 글자·선 두께나 선명도를 보증하지 않는다. 목록 결론 칩은 30px override여서 약 19.8px지만 새 결론의 짧은 노출 시간 문제는 그대로다. 중요한 선이 3px 이상이어야 한다는 1라운드 계약도 별도로 적용해야 한다. 최종 출력·실제 시청 크기의 읽기 성공 여부는 시트로 판단 불가다.

### 3-6. 틀 예고와 범용화 범위

`ghost()`는 틀 전용 wrapper가 아니라 선택된 카드 전체에 blur와 opacity를 적용한다. `.cv-num` 같은 라벨은 자식 리빌로 분리되지 않아 함께 옅어지고 먼저 보인다. ‘완전히 빈 틀만 예고하고 본문은 선명하게’라는 계약과 정확히 같지 않다. 문서의 ‘첫 카드만 틀 예고’ 설명도 실제 흐름의 `.n0/.n1`, 비교의 `.k/.L/.R/.R-sub` 호출과 맞지 않는다.

채택한다면 틀과 내용을 분리하고 blur는 기본 기능에서 빼는 쪽을 권한다. `ghost`, `swap`, `xfade`, `chips`를 한 번에 렉시콘에 올릴 이유도 없다. 이번 네 장면에서 사용·검증한 기능과 미사용 기능을 구분해야 한다. 공용 CSS의 `.cv-*` 규칙도 모두 `.slide--canvas` 아래로 제한된 것은 아니므로 ‘옵트인이라 영향 없음’은 이름 충돌 감사 없이 확정할 수 없다.

## 4. 게이트 해석: 둔감성은 타당하지만 FAIL을 지울 근거는 아니다

### 4-1. 원점수와 계산 방식

| 유형 | A | B |
|---|---|---|
| 개념 | 100.0% FAIL | 100.0% FAIL |
| 흐름 | 100.0% FAIL | 71.4% WARN |
| 목록 | 100.0% FAIL | 83.1% FAIL |
| 비교 | 100.0% FAIL | 87.4% FAIL |

`check_motion.py`는 기본 경로에서 폭 320px의 회색 프레임을 10fps로 만들고, **0.5초 전 프레임과의 평균 절대차를 0.1초 간격으로** 계산한다. 단순히 1초마다 스틸을 비교하거나 매번 직전 프레임만 비교하는 검사가 아니다. 길이가 6초를 넘는 슬라이드에서 정지 비율이 75% 초과면 FAIL, 50% 이상이면 WARN이다.

**흰 배경에 작은 변화가 묻힌다는 해석은 계산 구조와 시트에 부합한다.** 예를 들어 전체 픽셀의 0.3%만 평균 밝기 200만큼 변하면 전역 평균은 약 0.6으로 eps=1보다 작다. 이는 설명용 산술 예시이며 실제 이 영상의 픽셀 면적 측정값은 아니다. 저대비 테두리·작은 글자·옅은 등장·대부분의 백색 공간은 전역 평균을 작게 만든다.

하지만 ‘모든 높은 정지 비율은 센서 한계다’까지 증명되지는 않았다. 시트에는 실제 읽기 홀드와 거의 빈 틀만 남은 구간도 있다. 게이트 원시 `d5` 시계열과 큐별 영상 영역 차분을 대조하지 않았으므로, 검출 누락과 실제 홀드가 각각 얼마인지는 미확인이다. 시트의 몇 장이 달라졌다는 사실은 100%라는 결과와 모순되지 않는다. 각 0.5초 변화가 계속 eps 미만일 수 있기 때문이다.

또한 `03_리스크.md`의 ‘반대였다’, ‘A·B 모두 FAIL’은 정확하지 않다. 흐름 B는 WARN이며, 세 카메라 장면 모두 B 점수가 낮아졌다. 오히려 **카메라가 픽셀 점수를 개선해 품질처럼 보이게 할 위험은 여전히 존재한다.** 이 결과로 실제 오해가 발생했다고 말할 수는 없지만, 그 위험이 반증된 것은 아니다.

### 4-2. 임계 완화 없이 실전에 적용하는 방법

1. **원검사를 그대로 유지한다.** eps, FAIL/WARN 임계, 320px 분석 폭, 측정 범위를 점수 개선 목적으로 바꾸지 않는다. `--warn-only`를 이용한 우회나 카메라 route 일괄 면제도 하지 않는다. 현재 결과는 연구용 FAIL/WARN으로 남긴다.
2. **타임라인 기록과 영상 증거를 분리한다.** `fromTo` 시작 시각 목록은 ‘계획된 트윈’이다. 길이 고정용 opacity 1→1, 카메라 이동, 틀 등장도 들어 있으므로 ‘실제 가시 리빌 기록’이라고 부를 수 없다.
3. **의미별 가시성 감사표를 추가한다.** 큐 어절·로컬 시각·target·DOM 등장 시작·화면 안에 들어온 시각·읽을 크기와 대비에 도달한 시각·읽기 홀드·잘림 여부를 연결한다. 실제 출력의 큐 직전/직후와 팬 도중 프레임을 근거로 남기고, ROI 변화는 전역 게이트의 보조 증거로 사용한다. ROI 변화만으로 의미 전달 성공을 판정하지 않는다.
4. **높은 정지 점수를 분류한다.** 의도된 읽기 홀드, 실제 무내용 대기, 의미 있는 작은 변화의 검출 누락을 Scene별로 나눈다. 검출 누락을 입증하지 못했으면 ‘미확인’이다. 오너가 단순히 ‘괜찮아 보인다’고 말한 것을 자동 PASS로 변환하지 않는다.
5. **생산 차단 규칙과 보조 판단의 관계를 명문화한다.** 기존 정책이 FAIL 출고 금지라면 현재 상태로는 출고하지 않는다. 예외 절차를 도입할 경우에도 개별 Scene의 근거와 책임 있는 판단을 기록하고 원 FAIL을 보존한다. 예외 정책이 없는 상태에서 ‘센서가 둔감하다’는 주석만 붙여 투입하지 않는다.
6. **완전한 영상으로 기존 파이프라인을 수행한다.** 이번 게이트는 클립 전체를 슬라이드 한 장으로 계산했으므로 실제 장면 간 전환·청크 경계·편 전체 리듬 검증을 대신하지 않는다. 점수를 맞추려고 슬라이드를 잘게 나누거나 장식 팬을 추가하지 않는다.

### 4-3. 자막 안전 검증도 명칭부터 고쳐야 한다

문서는 ‘전 프레임’이라고 쓰면서 10fps 검사라고 설명한다. B JSON의 프레임 수 146·187·224·259도 각 구간 길이에 대해 10fps 수준이다. **30fps 출력의 모든 프레임 검사가 아니다.** 샘플 사이 약 0.1초 안의 침범은 놓칠 수 있다. A JSON에는 장면별 0.0만 있어 프레임 수·검출 기준을 재확인하기도 어렵다.

현재 인정할 수 있는 결론은 ‘10fps로 검사한 자막 밴드에서 검출된 비흰색 비율이 0으로 보고됨’이다. 실제 30fps 출력의 모든 프레임, 검사 색상 임계·크롭 좌표·원본 해상도를 기록해야 한다. 무자막 소스의 빈 밴드는 최종 자막 합성 상태의 검수와도 다르다.

`02_접목안.md`는 부분 채택일 때 변경 항목을 1~5·7·8로 적어 자막 검사 개선인 6을 빠뜨렸다. **카메라를 하나라도 채택하면 경로 전체의 안전영역 검사는 함께 들어가야 한다.**

## 5. 채택 권고 갱신과 유형별 오너 질문

현재 자료로 정식 채택을 확정할 유형은 없다. 우선순위는 **흐름 카메라 재검증 → 개념의 상태 교체 독립 검증 → 비교 구도 재설계**다. 짧은 목록의 카메라는 기본값으로 삼지 않는다. 다음 질문은 각 클립 직후 실제 답을 적게 해야 하며 ‘그렇게 느꼈다’ 체크만 받아서는 안 된다.

| 유형 | 갱신 권고 | 오너 판정 질문: 유형별 3개 이내 |
|---|---|---|
| 비교 | **현재 `.k→.L→.R` 방식은 채택 보류.** 비교 기준과 양쪽 조건을 같이 남기는 구도로 재시험한다. | ① “혼자 볼 자료와 남에게 전달할 결과물은 각각 어떻게 다뤄야 하며, 그 차이의 기준은 무엇인가?” B에서 설명이 더 정확하면 이길 조건, 기준·조건 대응을 잊으면 질 조건이다. ② “조건을 비교하려고 이전 화면을 기억하거나 되감아야 했던 시점은 언제인가?” B의 읽기 크기 이득이 기억 부담보다 커야 한다. ③ “끝난 직후 두 조건을 한 번에 다시 설명할 수 있는가?” 최종 샷이 실제 회수에 도움이 되면 fit 후보, 너무 짧거나 작아 도움이 없으면 fit 기각이다. |
| 목록 | **고정 화면 우선.** 세 행이 충분히 읽히는 A1을 이길 때만 제한 적용한다. | ① “보고서·자료 정리·자동화 도구에서 각각 확인할 것은 무엇인가?” B에서 현재 행은 잘 읽혀도 앞 행 대응을 잊으면 진다. ② “못 읽거나 화면을 멈추고 싶었던 문구와 시점은 무엇인가?” B 확대가 실제 읽기 실패를 줄이면 이길 조건이다. ③ “마지막에 챙겨야 한다고 한 것과 전부 챙기지 않아도 된다고 한 것은 무엇인가?” 작은 결론 칩 때문에 ‘뼈대’ 결론이 남지 않으면 B는 진다. |
| 흐름 | **카메라의 가장 유력한 재시험 후보.** 출발점·분기 제목 잘림을 보정한다. | ① “업무 과정을 챙기는 방법 세 가지는 무엇이며, 서로 어떤 관계인가?” B가 세 갈래의 의미를 더 정확히 남기면 이긴다. ② “새 가지가 나타날 때 어디에서 연결됐는지 알 수 있었는가? 놓친 순간은 언제인가?” 카메라가 연결을 읽게 하면 이기고, 기존 가지를 잃게 하면 진다. ③ “끝난 뒤 첫 단계부터 세 가지 방법까지 설명할 수 있는가?” 전체 샷이 구조를 회수하고 새 정보 읽기를 방해하지 않아야 fit을 채택한다. |
| 개념 | **카메라와 분리하여 상태 교체 후보만 유지.** 틀 예고·blur의 추가 가치는 미확인이다. | ① “끝까지 같은 사람·대상으로 남은 것은 무엇이고, 달라진 것은 무엇인가?” B가 정체성과 변화를 더 정확히 남기면 이길 조건이다. ② “일을 전달한 것과 보고를 받지 못한 것을 각각 설명할 수 있는가?” 옅은 라벨·연결선 때문에 두 관계를 혼동하면 진다. ③ “처음의 틀과 상태가 바뀌는 순간에 무엇이 진행되는지 이해했는가, 기다리거나 두 문장을 겹쳐 읽은 순간이 있었는가?” 틀 예고가 준비를 도왔을 때만 유지하고, 차이가 없으면 효과를 줄인다. |

개념 B가 이겨도 ‘제자리 상태 교체만’과 ‘제자리 교체+틀 예고’를 후속으로 나눠야 한다. A에도 같은 카드 안 상태 교체가 있으므로 B의 우위를 제자리 배치 하나의 효과로 귀속할 수 없다.

네 샘플은 유형별 실패 조건을 찾는 사례다. 오너 한 명의 선호·재설명 결과를 시청자 이해도나 유지율 향상의 통계적 증거로 일반화하지 않는다. 비슷하면 유지비가 낮은 현행을 택한다는 기준은 유지하되, 그 결정 규칙은 첫 시청 전에 기대를 주는 문구로 보여주지 않는 편이 낫다.

## 6. 오너 판정 페이지 비평

### 6-1. 유지할 점

X/Y로 명칭을 가리고 한 번에 한 클립씩 보도록 한 점, 미감보다 이해와 가독성을 먼저 묻는 방향, 개념 쌍과 카메라 쌍을 구분한 설명은 적절하다. 비교·개념 A→B, 목록·흐름 B→A 배치는 1라운드의 제안을 따랐으며 전체 첫 노출 수는 균형을 이룬다.

다만 이것은 **고정된 교차 배치**이지 매번 무작위로 섞는 절차는 아니다. 현재 페이지의 ‘순서 섞음’은 무작위화로 오해되지 않도록 표현을 바꾸면 된다.

### 6-2. 편향과 기록 결함

| 문제 | 실제 페이지 요소 | 수정 권고 |
|---|---|---|
| 실험 가설이 미리 노출됨 | 제목부터 ‘캔버스 카메라’이며 상단에 ‘연출 방식 하나뿐’이라고 쓴다. | 첫 판정 화면은 중립적인 ‘설명 영상 비교’로 제시한다. 세 유형은 동일 캔버스의 프레이밍 실험, 개념은 등장·상태 전환 묶음임을 관리용 설명에 정확히 기록한다. |
| 정답을 제목에서 가르침 | 비교 제목에 ‘기준은 딱 하나, 나에게 책임이 있는가’, 흐름 제목에 ‘노하우 3가지’가 있다. | 첫 재설명 전에 내용의 정답·구조를 제목과 질문으로 알려주지 않는다. 장면 번호만 보여주고 중립적인 자유 재설명을 먼저 받는다. |
| 목록 B에 불리한 유도 질문 | ‘이미 한 화면에 들어오는 목록에 이동을 더하면 도움이 되는가?’, ‘카메라가 지는 것도 중요한 결과’. | 실패 사례를 찾으려는 의도는 좋지만 참가자에게 기대 답을 암시한다. 세 예시에서 기억한 내용을 먼저 묻고, 이동 효용은 2차 검수에서 질문한다. |
| 개념 B의 의도도 미리 제시 | ‘상태 교체가 같은 대상의 변화로 읽히는가?’ | 먼저 무엇이 바뀌었는지 자유롭게 쓰게 한다. 답을 받은 다음 정체성 추적 질문으로 좁힌다. |
| 실질적인 블라인드가 약함 | 첫 응답 전에 B의 이동 방식·fit 배율·점수·채택 기준을 볼 수 있다. | 게이트, 구현 설명, ‘비슷하면 A’, 정답 라벨은 양쪽 첫 응답 제출 뒤 공개한다. 움직임 자체를 숨길 수는 없지만 새 기능에 대한 기대 효과는 줄일 수 있다. |
| 클립별 실제 답을 보존하지 않음 | ‘한 문장으로 말할 수 있었다’ 체크 두 개와 쌍당 textarea 하나다. | X 직후와 Y 직후 각각 재설명 입력칸·시점 메모를 둔다. 이해했다고 느낀 정도와 실제 답의 정확성을 구분한다. |
| 미응답이 실패로 저장됨 | 내보내기에서 `checked ? '예' : '아니오'`를 쓴다. | 예/아니오/미응답 또는 명시적인 선택으로 저장한다. 미응답·판단 불가·해당 없음도 구분한다. |
| 체크가 이중 질문임 | ‘못 읽은 글자·멈추고 싶은 순간 없음’. | 못 읽은 문구와 멈추고 싶은 시점을 따로 적게 한다. 읽을 수 있어도 내용 정리를 위해 멈추고 싶을 수 있다. |
| 두 번째 노출의 학습 효과 | 언제나 X를 먼저, Y를 다음에 보며 같은 내용을 반복한다. | 오너 평가는 정성 판정임을 명시한다. 다른 평가자가 있으면 같은 유형의 첫 노출을 A/B로 균형 배정한다. 같은 오너에게 역순 재시청시키는 것만으로 첫 노출 효과가 제거되지는 않는다. |
| 실제 출고본이 중간에 열림 | 각 장면 아래 참고 영상이 먼저 열 수 있는 `details`로 있다. | 전체 첫 판정 뒤 별도 단계로 옮긴다. 출고본에 대한 익숙함과 신뢰가 X/Y 응답에 섞이지 않게 한다. 흐름에는 참고본이 없는 차이도 기록한다. |
| 표시 크기 통제가 없음 | `.pair`는 항상 2열이고 영상은 각 열 폭의 100%다. | 첫 시청은 같은 단일 플레이어 영역에서 하나씩 보여준다. 실제 시청 크기·전체화면 여부를 통제한다. 현재 작은 2열 표시가 작은 글자에 불리하게 작용할 가능성은 추측이며, 실제 브라우저 크기는 이번에 검증하지 않았다. |
| 동시 재생 방지는 안내뿐 | 두 video가 독립 controls를 가진다. | 하나를 시작하면 다른 영상을 정지시킨다. 첫 판정 뒤에만 동시 검수 UI를 제공한다. |
| 기록 보존이 약함 | ‘답변 내보내기’는 textarea에 텍스트를 만들고 선택할 뿐 실제 파일 저장은 하지 않는다. 버전·시청 크기·재생 순서·반복 횟수도 기록하지 않는다. | 다운로드 또는 명확한 복사 절차를 제공하고, 클립 버전과 실제 순서·반복 여부를 기록한다. 첫 응답을 수정하기 전 원응답을 보존한다. |

오너가 보게 할 순서는 **중립적인 장면 번호 → X 단독 시청과 실제 재설명 → Y 단독 시청과 실제 재설명 → 쌍 선호와 불편 시점 → 기술 자료·출고본·정답 공개**가 적절하다. 질문의 답을 미리 제목에 써 놓거나 체크박스만으로 이해 성공을 선언하는 부분을 먼저 고쳐야 한다.

## 7. 이번 결과로 확정할 수 있는 범위

확정할 수 있는 것은 카메라를 별도 wrapper와 로컬 타임라인으로 구현할 수 있고, 같은 캔버스의 세 장면에서 A/B 콘텐츠를 일치시켰으며, 흐름 한 구간의 반복 캡처가 일치했다는 점이다. 확정할 수 없는 것은 카메라의 전반적 우위, 모든 장면의 seek 안전, 출력 전 프레임의 자막 안전, 정상 재생에서의 큐·가독성 통과다.

**최우선 수정 대상은 효과의 세련됨이 아니라 비교 기준 보존, 결론의 읽기 시간, 검증 증거의 정확성이다.** 이 세 가지를 고친 뒤 이긴 유형의 필요한 기능만 편입하라. 현재 자료만으로 헬퍼 전부·preset 다섯 개·세로 화면까지 함께 표준화하는 것은 권하지 않는다.

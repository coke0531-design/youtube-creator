# 접목안: 캔버스 카메라를 youtube-creator에 넣는 방법

기준: `01_레퍼런스_분석.md`(레퍼런스 문법) + 코드 조사(현행 템플릿·게이트) + astra 1라운드(`_advice/astra_r1.md`).
상태: **실험용 구현 완료, **2026-09-14 정식 편입 완료(오너 판정 V2 채택 — `결과물/2026-09-14_풀링013_1분비교_현행vs캔버스카메라/`). §3 표 1~8 반영, 9(9:16)는 보류**.** 오너 판정(`결과물/2026-09-13_캔버스카메라-AB실험/비교_보기.html`) 뒤에 채택 범위를 정한다.

## 1. 현행 시스템에서 확인된 사실 (코드 조사)

- "카메라"라는 구현은 0건. `camera-with-intent`는 route 이름만 있고 정의·구현·검사가 없다(`check_storyboard.py`는 이름만 통과시킨다).
- 카메라에 가장 가까운 것은 `.nudge`(그룹 `translateX` 1회 이동). 줌스루/인버스 줌 preset은 design.md에만 있고 템플릿 CSS에 없다.
- 슬라이드 자체 `transform`이 전환에 쓰이므로 카메라는 **별도 래퍼 레이어**여야 한다(이중 구동 금지).
- 캡처 결정론의 근거는 `__capture.seek(t)`가 시계 없이 좌표를 찍는 것(GSAP `totalTime` 2호출·WAAPI currentTime·카운터 수식). 카메라도 이 경로를 타야 한다.
- `슬라이드-디자인.md` "scale 0.88~1.08 초과 금지"와 design.md 벡터 예약표 "Z 후퇴 = 파트 타이틀 전용"은 카메라 레이어에 예외 명시가 필요하다.
- 스토리보드 파서의 `vec.axis`는 이미 z를 허용한다. `REVEAL_HINT`에 "카메라·팬·줌·유령" 어휘가 없어 카메라 Scene이 리빌로 안 잡힐 수 있다.

## 2. 실험 구현 (astra 3안 중 ① 최소안 + ②의 헬퍼만)

위치: `결과물/2026-09-13_캔버스카메라-AB실험/B_캔버스카메라/_parts/`
- `canvas-camera.css`: 옵트인 `.slide--canvas` + `.cam`(뷰포트, overflow hidden) + `.canvas`(카메라 대상, transform-origin 0 0) + 카드·칩·선 어휘(`.cv-card` `.cv-item` `.chip` `.chip--fill` `.chip--mono` `.chip--amber` `.chip--green` `.chip--x` `.cv-line`).
- `canvas-camera.js`: `window.__cam` 헬퍼. 전부 GSAP `fromTo`, 슬라이드 로컬 타임라인 안에서만 쓴다.
  - `shot(tl, canvasSel, targets, at, {pad, dur, ease})` 대상(들)의 합집합 사각형을 자막 안전영역 위 가운데에 잡는다.
  - `fit(tl, canvasSel, at, {targets})` 지정한 대상 전부를 잡는다(전체 보기). 대상은 명시(`.cv-item` 기본).
  - `ghost(tl, sel, at)` 틀 예고(옅음+살짝 흐림 → 선명. 카드 안 작은 라벨은 틀과 함께 옅게 보이고, 내용은 별도 fade 큐). `fade(tl, sel, at)` 내용 선명 등장. `draw(tl, sel, at)` 선 그어짐(`data-head`로 화살촉 뒤따름). `swap(out, in)` 제자리 상태 교체. `xfade(out, in)` 소장면 교차.
  - 지원 범위 = 새 페이지 + 순방향 seek(캡처 경로). 역방향·임의 순서 seek는 템플릿이 지원하지 않는다.
  - 규칙 3개가 코드에 박혀 있다: ① 카메라 scale ≤ 1(클로즈업이 1배, 전체 보기는 축소. 텍스트 래스터 흐림 방지) ② 요소마다 첫 트윈만 `immediateRender`(뒤 단계 트윈이 빌드 시점 화면을 덮는 GSAP 함정 차단, 실측으로 잡음) ③ 카메라 from 값은 항상 직전 카메라 상태(연속성 = 역방향 seek에도 상태가 맞음).
  - `window.__CAM_FIXED = true`면 첫 호출에서 `data-fit` 대상을 잡고 이후 이동을 무시한다(A안 = 카메라 고정 비교군).
- 좌표는 디자인 px(1920×1080). 카드는 `left/top/width/height`를 명시해 폰트 로딩과 무관하게 카메라 좌표가 결정된다.

## 4. 채택 범위 후보 (오너 판정에 따라)

- **전부 채택**: 비교·흐름·목록·개념 4유형 모두 B가 낫다고 판정될 때. 위 표 1~9 전부. 헬퍼 중 이번 4장면에서 실제로 쓴 것은 shot/fit/ghost/fade/draw/swap이고 xfade·chips는 미검증이라 렉시콘 등재는 쓴 것만.
- **부분 채택(astra 권고, 기본값)**: 카메라는 B가 이긴 유형에만(2라운드 예상 순위: 흐름 > 개념의 상태 교체 > 비교 재설계 후 > 목록은 고정 우선), 틀 예고·제자리 교체는 카메라 없이도 효과가 있으면 별도 preset으로. 표 1~8 전부(카메라를 하나라도 채택하면 6의 전 프레임 자막 검사는 필수).
- **기각**: A와 비슷하거나 이해가 나빠질 때. 실험 폴더만 남기고 템플릿·문서 변경 없음. `_parts/`는 보관.

## 5. 유지보수 비용 (실측)

- 4장면 B 제작(마크업+타임라인) 약 1시간, A 파생(고정 카메라 + 개념 현행판) 약 20분, 캡처 4구간 약 4분(2560×1440 30fps), 재캡처 1구간 약 1분.
- 한 문구를 바꾸면 카드 크기가 고정이라 카메라 좌표는 안 바뀐다(줄바꿈·넘침은 확인 필요). 카드를 옮기면 타임라인을 다시 만들 때 그 카드를 포함한 shot/fit 전부가 재계산된다(헬퍼가 offset을 읽음). SVG 연결선 path 좌표는 손으로 옮겨야 한다.

## 2. `scripts/check_motion.py` — 모션 실측 게이트 (결정론)

### 사용법

```bash
python scripts/check_motion.py "결과물/2026-08-06_풀링013_클로드_일잘러_노하우"
python scripts/check_motion.py <capture.mp4> --timeline <타임라인.json>
python scripts/check_motion.py <작업폴더> --json --warn-only
# 임계 조정: --eps 1.0(정지 판정, 평균 절대차 0~255) --fail 0.75 --warn 0.50 --min-len 6 --width 320
```

### 방식

`imageio_ffmpeg.get_ffmpeg_exe()`(다른 스크립트와 동일 획득 방식)로 ffmpeg 1회 실행 —
`fps=10,scale=320:180,pix_fmt=gray,f=rawvideo`를 stdout으로 스트리밍해 링버퍼로 읽는다.

- `d5[k] = mean|f[k] − f[k−5]|` → **0.5초 격자 차분**. 슬라이드 구간 안의 샘플 중 `< eps`인 비율 = 정지 비율.
- `d1[k] = mean|f[k] − f[k−1]|` → **0.1초 인접 차분**. 슬라이드 경계 t의 `t−0.1`·`t+0.1` 판정용.

판정
- 슬라이드 길이 > 6s이고 정지 비율 > 75% → **FAIL**, 50~75% → WARN, 그 외 OK
- 경계 양쪽 다 정지 → **죽은 박자 WARN**, 한쪽만 정지 → 참고(half) 집계
  (나가는 슬라이드가 멈춘 뒤 컷되는 현행 크로스페이드 패턴이 여기 잡힌다)

numpy가 없으면 ffmpeg `freezedetect=n=0.001:d=1.5` 폴백으로 정지 구간만 계산한다(죽은 박자 검사 생략).

### 자기 검증 — 풀링013 현행 산출물 (회귀 기준선)

입력: `결과물/2026-08-06_풀링013_클로드_일잘러_노하우/04_영상소스/capture.mp4` (411.77s, 2560x1440, 42슬라이드)
+ 같은 폴더 `타임라인.json`. 실행 시간 **약 23초**.

```
판정 대상(>6s) 35개 · 평균 정지 비율 97.2% · FAIL 35 · WARN 0 · OK 0   → exit 1
죽은 박자(양쪽 정지) 0건 / 한쪽 정지 컷 41건 (경계 41개 전부)
```

- 최악 S29 99.2%, S42 99.2%, S02 98.5% / 최선(판정 대상) S24 95.4%
- 6s 이하 7개 슬라이드도 실측 정지 비율은 93.8~97.8%로 동일하다(길이 조건으로 판정 제외될 뿐)
- 진단 문서의 "슬라이드 시간의 80~90%가 정지 화면"은 **실측 97.2%로 오히려 과소평가**였다
- 경계 41개 전부 `before≈0.0`(나가는 슬라이드 완전 정지) + `after` 3.96~13.56(들어오는 쪽만 움직임) —
  §3-3 벡터 법칙이 지적한 "속도 불일치 컷"이 전수로 확인된다
- 진단 통계: `d5` 중앙값 0.0 / p90 0.126 vs 모션 순간 3~14 → `eps=1.0` 기본값이 두 분포 사이에 안전하게 위치

즉 **현행 산출물이 35/35 FAIL로 잡히는 것이 정상**이며, 이 수치가 v2 개편의 비포(before) 기준선이다.

### 한계

- 컨텐츠 무관 밝기 변화(페이드·배경 애니메이션)도 "모션"으로 계산한다. 반대로 아주 작은 요소만 움직이는
  구간은 320px 다운스케일에서 평균이 희석돼 정지로 잡힐 수 있다(→ `--width`로 조정).
- `capture_slides.py`가 매 프레임 토글하는 좌상단 2px damage 픽셀은 320px 스케일에서 평균 기여가 무시할
  수준이라 판정에 영향이 없다(실측 d5 중앙값 0.0).
- 죽은 박자 검사는 ±0.1s 두 점 표본이다. 전환 길이가 0.2s 미만이면 놓칠 수 있다.
- 슬라이드 경계 시각은 `타임라인.json`을 신뢰한다(영상에서 컷을 재검출하지 않는다).

## 3. `scripts/hf_audit.py` — HF 브라우저 감사기 주입

### 벤더 발췌

`C:\Workspace-Hub\공유 프로젝트\hyperframes`(커밋 `7170dc63ae78dba6ddb211179b453bedf74932a6`, 2026-08-26,
Apache-2.0)의 `packages/cli/src/commands/` 3파일을 `벤더/hf-audit/`로 **무수정 복사**하고 각 파일 상단에
출처 주석(리포 URL·커밋·라이선스·수정 여부·갱신 금지 정책)을 덧붙였다. 본문 바이트는 원본과 동일.

- `layout-audit.browser.js` — `window.__hyperframesLayoutAudit({time, tolerance})`
- `contrast-audit.browser.js` — `__contrastAuditPrepare()` → 스크린샷 → `__contrastAuditFinish(b64, t, cands)`
- `motion-sample.browser.js` — `window.__hyperframesMotionSample({selectors, livenessScopes})`

**한글 재보정**: 원본 `const ATOMIC_LABEL_MAX_CHARS = 16;`(라틴 기준 "한 단어 라벨" 판정)을 주입 시점
문자열 치환으로 **8**로 낮춘다(`--atomic-max`로 조정). 벤더 파일 자체는 고치지 않는 런타임 오버라이드다.
명암비 임계는 원본 유지(큰 텍스트 3:1 / 작은 텍스트 4.5:1).

### 사용법

```bash
python scripts/hf_audit.py "결과물/2026-08-06_풀링013_클로드_일잘러_노하우"
python scripts/hf_audit.py <presentation.html> --timeline <타임라인.json>
python scripts/hf_audit.py <작업폴더> --json --out audit.json
# 옵션: --size 2560x1440  --atomic-max 8  --limit N(디버그)  --warn-only  --storyboard <경로>
```

동작: playwright headless chromium으로 `presentation.html?capture=1` 로드 → `__capture.ready` 대기 →
3스크립트 주입 → 샘플 시점마다 `__capture.seek(t)`(오름차순, 덱의 seek이 단조 증가라 정렬 필수) →
레이아웃 감사 · 명암비 2단계(prepare → 뷰포트 스크린샷 → finish) · 모션 서명 수집.
샘플 시점 = **슬라이드 중간 지점** + (STORYBOARD.md가 있으면) **각 Scene 경계 + 0.5s**.
FAIL 조건 = 레이아웃 `severity: error` 또는 명암비 실패. 레이아웃 `warning`은 카운트만 한다.
`--json`은 stdout을 JSON 전용으로 비우고 진행 로그는 stderr로 보낸다.

**고의 파손 검출 확인**: `04_영상소스/__hf_audit_break.html`(원본 사본에 `color:#efefef` / 흰 배경 텍스트

### 한계

  기다린다. 같은 시점을 두 번 돌리면 진행 중 애니메이션 상태에 따라 findings가 달라진다

  개별 finding은 재현 확인 후 판단할 것. (§3-3 GSAP seek-safe 타임라인이 들어오면 결정론에 가까워진다.)

- `content_overlap` 44건은 대부분 `h2.el > strong` 같은 **인라인 강조가 부모 텍스트와 겹치는 구조**를
